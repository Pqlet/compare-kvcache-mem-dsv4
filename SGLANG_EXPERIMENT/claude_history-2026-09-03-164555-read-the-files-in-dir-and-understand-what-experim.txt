● Here's what this experiment is doing, in plain terms:

  Goal: Validate a theoretical KV-cache memory model (compare_kv_cache.py, one
  level up) against a real SGLang server running DeepSeek-V4-Flash, by actually
  serving the model and benchmarking it at various context lengths.

  The setup (SGLANG_EXPERIMENT/):
  1. GUIDE.txt — bootstrap steps: create a venv, clone sglang at a pinned commit
     (a1fe4e30), install it editable, and fix a FlashInfer cubin/JIT-cache
     mismatch left over from the base image.
  2. sglang_serve.sh — launches the actual server: DeepSeek-V4-Flash, TP=8,
     fp8_e4m3 KV cache dtype, mem-fraction-static=0.85, 1M context length,
     metrics endpoints enabled, logging to sglang_dsv4.log.
  3. bench_kv.sh — the actual benchmark driver. For a set of input lengths (only
     524288 is currently uncommented — others up to 1024 are commented out, so
     it looks like they already ran the smaller ones and are focused on the 512K
     case now), it:
     - flushes the KV cache,
     - starts a background sampler that scrapes /metrics (Prometheus) and
       nvidia-smi every 0.1s,
     - runs sglang.benchmark.serving with --tokenize-prompt --random-input-len 
       <N> --num-prompts 1 --max-concurrency 1,
     - captures a final /metrics snapshot after the request completes.
  4. summarize_kv.py — post-processes all the .prom files under
     kv_bench_sglang/<context>/, extracting peak kv_used_tokens,
     kv_evictable_tokens, min kv_available_tokens, and
     full_token_usage/swa_token_usage, printed as a table per context length.
     Output of this is kv_tokens.txt.

  What they found (kv_tokens.txt): token-level usage tracks linearly with input
  length as expected (e.g. 524288 input → 524544 used/evictable tokens), and
  full_token_usage grows from ~0.0002 to ~0.0765 across the sweep — i.e. real
  utilization of the pool.

  manual_logs.txt is a scratchpad of manual greps/curls: pulling DSV4 memory 
  calculation/DSV4 pool sizes lines from the server log (e.g.
  bytes_per_full_token=7033.45, full_token=6859008) and hitting /model_info for
  kv_cache_info.

  kv_memory.txt looks incomplete/stale — it's all zeros ("Effective
  bytes/full-token: 0.00", all GiB columns 0.000), so whatever script/command
  produced that (probably meant to compute actual GiB usage from kv_cache_info
  or nvidia-smi deltas) didn't work yet — that part of the analysis is
  unfinished.

  How it connects to compare_kv_cache.py: that script (parent dir) computes
  theoretical per-token/per-GPU byte costs for V3.2 vs V4-Flash from static
  config math (configs/*.json), producing results.csv. There's a small pending
  fix in the diff: the V4-Flash main_bytes_per_entry formula was corrected from
  non-RoPE stored as FP8 (nope_dim) to BF16 (nope_dim*2), per the
  SGLANG_DSV4_COMPRESS_STATE_DTYPE=bf16 env var set in sglang_serve.sh — i.e.,
  the live server run informed a correction to the theoretical estimator.

  So overall: this is a real end-to-end validation harness — spin up actual
  DeepSeek-V4-Flash on 8 GPUs, sweep context lengths, scrape real Prometheus/GPU
  metrics, and reconcile them against the analytical byte-cost model in
  compare_kv_cache.py. The kv_memory.txt GiB comparison (the part meant to
  compare actual measured GPU memory bytes against the theoretical estimate) is
  the one piece that's still broken/unfinished.

  disagree.

● 2) Why the 3.6/3.7 GB is per-GPU, not divided across the cluster:

  Every one of the 8 TP ranks reports the identical pool size (full=6859008,
  c4=1714752, c128=53586, ... — byte-for-byte the same on TP0 through TP7). If
  the KV cache were sharded across tensor-parallel ranks (the way standard
  MHA/GQA key/value heads are split), each rank would show roughly 1/8th the
  capacity. It doesn't — every GPU allocates a full, independent copy.

  That's because DeepSeek's attention (MLA-lineage, inherited into CSA/HCA)
  caches a compressed latent vector, not per-head K/V — and that latent isn't
  head-parallel, so TP has nothing to shard it by. Each GPU must materialize the
  full compressed cache locally to run its share of attention. So "3.6/3.7 GB"

  portable unit (how much cache one accelerator must hold for one sequence), not
  something that depends on cluster size.

❯ no, i mean why the 54 GB estimate was wrong before ?                          

● Good clarifying question — and the answer is neither. The ~54GB error had
  nothing to do with seqlen compression or precision; it was a pool-accounting 
  mismatch: pricing real tokens with a constant that pays for a different pool
  they don't belong to.

  Here's the mechanism, now that we've traced the actual formula:

  - bytes_per_full_token (7033.45) already accounts for CSA/HCA compression 
    correctly — its formula (pool_configurator.py:879-913) includes c4_frac × 
    kv_bytes × num_layers_ca4 and (1/128) × kv_bytes × num_layers_ca128, i.e.
    the 4x/128x seqlen ratios are baked in. So it's not a seqlen bug.
  - It also uses the same FP8/BF16 byte layout (584 bytes/entry) as everywhere
    else. So it's not a precision bug either.
  - The actual problem: that formula has an extra term, swa_ratio(0.1) × 
    kv_bytes(584) × num_layers_total(43) ≈ 2511 bytes, which reserves capacity
    for the SWA/state pool — spread proportionally across all 43 layers —
    because bytes_per_full_token is meant to price one slot of total pool 
    capacity, and each slot of capacity has to fund both the classical (c4/c128)
    pool and its co-allocated state pool.
  - But kv_used_tokens only counts occupancy of the classical pool. The
    SWA/state pool is separately tracked (swa_used_tokens, fixed capacity
    max_total_num_tokens_swa, doesn't scale with context).

  So multiplying kv_used_tokens (classical-pool-only real usage) by
  bytes_per_full_token (a rate that includes a subsidy for the other pool)
  overcharges every real token for capacity it isn't consuming. That's a
  bookkeeping/scope error — using a "price per slot of total budget" as if it
  were "price per token actually stored" — not a compression-model error. Once I
  isolated just the classical-pool terms (584 bytes/entry ÷ 4 or ÷128 by layer,
  no SWA subsidy), the rate dropped from 7033.45 to 3850.25 bytes/token
  (~1.83x), and the cluster estimate came down from ~54GB to ~15GB at 524K
  tokens (proportionally ~30GB at 1M) — matching the paper.

  No direct, out-of-the-box measurement exists today. Three attempts, three dead

  1. sglang:kv_cache_memory_usage_gb — the metric built for exactly this — is
     unpopulated for DSV4 (always 0), because the DSV4 pool classes never

  3. No other SGLang endpoint exposes it as a ready-made number.

  But "unmeasurable" and "unknowable" aren't the same thing. GPU memory itself
  has no concept of "used vs. free bytes within an already-reserved buffer" —
  that information only exists as allocator bookkeeping (which slots are
  assigned to live requests). SGLang already tracks that bookkeeping in token
  units (kv_used_tokens, live, real, updated every scrape). The only thing
  missing is turning that token count into bytes — and we now have the
  byte-per-token constant verified directly from SGLang's own source (not
  guessed), cross-checked two ways (matches an assert in one file, matches a
  formula in another, and reproduces the logged bytes_per_full_token bit-for-bit
  once the pool-capacity terms are backed out).

  So: kv_used_tokens × (source-verified bytes/token) is functionally the same 
  computation a correctly-implemented kv_cache_memory_usage_gb would have to do
  internally — GPU memory has no other way to answer "how many bytes are
  occupied right now" for a pre-allocated pool. The difference between what we
  have and a "real" measurement isn't a different number, it's where the
  multiplication happens: SGLang could do it live inside the process and expose
  it as a gauge (the fix I described earlier, not yet applied); we're doing the
  same arithmetic externally from logs and /metrics.
